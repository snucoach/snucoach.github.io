# 스누코치 회원 기능 설정 가이드

홈페이지(GitHub Pages)는 정적 사이트라서 데이터베이스를 직접 둘 수 없다.
회원 계정·DB는 **Supabase**(무료 플랜)에 두고, 사이트는 브라우저에서 Supabase와 통신한다.
이 문서 순서대로 한 번 설정하면 회원가입·로그인·마이페이지·비밀번호 찾기·회원 탈퇴·관리자 회원 목록·회원 후기가 동작한다.

예상 소요 시간: 30~40분 (카카오 로그인 제외)

---

## 0. 무엇이 어디에 있나

| 경로 | 내용 |
|---|---|
| `login.html` `signup.html` `reset-password.html` `account.html` `admin.html` | 로그인 · 회원가입 · 비밀번호 찾기 · 마이페이지 · 회원 관리(관리자) |
| `privacy.html` `terms.html` | 개인정보처리방침 · 이용약관 (모든 페이지 푸터에 링크). 고치기 전 문서는 `privacy-YYYYMMDD.html` `terms-YYYYMMDD.html` |

## 1. Supabase 프로젝트 만들기

1. https://supabase.com 가입 → **New project**
2. 입력
   - Name: `snucoach`
   - Database Password: **Generate** 로 만들고 안전한 곳에 보관(사이트에는 절대 넣지 않음)
   - Region: **Northeast Asia (Seoul)** ← 개인정보처리방침에 ‘서울 리전’으로 적었으므로 반드시 서울
   - Plan: Free
3. 프로젝트가 만들어질 때까지 1~2분 기다린다.

## 2. 데이터베이스 설정 (SQL 한 번 실행)

1. 왼쪽 메뉴 **SQL Editor** → **New query**
2. `supabase/migrations/20261001000000_members.sql` 파일 내용을 **전부** 복사해 붙여 넣고 **Run**
3. 결과가 `Success` 이면, **New query** 를 한 번 더 눌러 나머지 파일도 **파일 이름 순서대로** 같은 방법으로 Run
   - `20261001010000_target_alerts.sql`
   - `20261002000000_phone.sql`
   - `20261002010000_phone_alert_enforce.sql`
   - `20261003000000_reviews.sql`
4. 모두 `Success` 이면 끝. (여러 번 실행해도 같은 결과가 되도록 만들어 두었다)

만들어지는 것: 회원 프로필 표(휴대전화 번호, 이메일·문자 수신 동의 포함), 본인 정보만 보이게 하는 보안 규칙(RLS), 회원 탈퇴 함수, 관리자 회원 목록 함수, 3개월 지난 로그인 기록 자동 삭제 작업, 회원 후기 표와 공개 조회용 뷰·관리자 함수.

`20261003000000_reviews.sql` 은 `…_members.sql` 만 있으면 된다. 휴대전화용 두 파일보다 먼저 실행해도 되고, 다시 실행해도 후기와 처리 기록이 그대로다.

> **항상 파일 이름 순서대로 실행한다.** `20261002000000_phone.sql` 을 실행한 뒤에는 앞의 두 파일(`…_members.sql`, `…_target_alerts.sql`)을 다시 실행하지 않는다.
> 다시 실행하면 관리자 목록 함수에서 오류(42P13)가 난다. 실수로 실행했다면 `20261002000000_phone.sql` → `20261002010000_phone_alert_enforce.sql` 순서로 한 번 더 실행하면 원래대로 돌아온다.
> 그 사이에 가입한 회원이 있으면 2-1 의 「SQL ① 을 다시 실행할 때」를 따른다.

### 2-1. 운영 중인 프로젝트에 휴대전화 번호 적용 (2026년 10월)

이미 회원이 있는 프로젝트에는 **반드시 아래 순서로** 적용한다. 기존 회원 정보는 바뀌지 않는다(번호는 비어 있고 문자 수신은 미동의).

0. **날짜 점검.** `node supabase/local/privacy-dates.mjs` 를 실행한다. 「배포하지 않습니다」가 나오면 여기서 멈춘다(9절 첫 항목).
1. **SQL ①** `20261002000000_phone.sql` 을 SQL Editor 에서 Run. **사이트 배포보다 먼저 실행한다(필수).**
   - 확인: 지금 사이트(옛 화면)에서 로그인, 회원 정보 저장, 알림 신청, 회원 관리 화면이 그대로 되는지 본다.
   - SQL ① 실행 뒤 확인: 아래 조회가 `0` 이어야 한다(가입 정보에 번호 사본이 남아 있지 않다).

```sql
select count(*) from auth.users where jsonb_typeof(raw_user_meta_data) = 'object' and raw_user_meta_data ? 'phone';
```

2. **사이트 배포**(새 화면).
   - 확인: 새 가입(번호 필수), 구글·카카오 가입 마무리, 기존 회원의 번호 입력 카드, 알림 신청 창, 회원 관리의 휴대전화·문자 수신 열.
   - 회원 관리 화면에서 기존 회원의 문자 수신이 모두 `-` 인지 본다(이메일 수신 동의는 문자 동의로 넘어가지 않는다).
   - **새로 가입한 계정이 하나 생기면 1번의 확인 조회를 다시 실행한다.** `0` 이 아니면 가입 트리거가 가입 정보의 번호 사본을 지우지 못한 것이다(실제 인증 서버에서는 이 동작을 미리 확인하지 못했다). 아래 「SQL ① 을 다시 실행할 때」의 2~4번으로 정리하고 원인을 살핀다.
3. **SQL ②** `20261002010000_phone_alert_enforce.sql` 은 배포 다음 날 이후에 Run. (브라우저에 옛 화면이 남아 있는 동안 실행하면, 그 화면에서 번호 없는 회원의 알림 신청이 ‘신청하지 못했습니다’로 끝난다.)
   - SQL ② 를 실행하기 전에는 「알림 신청에는 번호가 필요하다」를 화면만 확인한다. 서버(DB)는 SQL ② 가 있어야 막는다.

순서를 어겨도 가입 자체는 깨지지 않지만, **동의 기록이 정확하려면 SQL ① 이 반드시 먼저**다.

| 상황 | 결과 |
|---|---|
| SQL ① 을 먼저(필수 순서) | 옛 화면은 추가된 열을 모르는 채로 그대로 동작한다 |
| 사이트를 먼저(하지 않는다) | 가입·로그인은 되고 마이페이지의 번호 칸·카드·문자 스위치는 숨겨진다. 그러나 그 사이 가입한 회원에게 세 가지가 어긋난다. ① 가입 완료 화면은 「마케팅 정보(이메일·문자) 수신 동의를 처리했습니다」라고 알리지만 **문자 수신 동의는 기록되지 않고 SQL ① 을 실행해도 옮겨지지 않는다**(미동의로 남는다. 그 회원에게 광고성 문자를 보내면 안 되고, 마이페이지에서 다시 켜야 한다). ② 번호가 가입 정보에만 남아 그 회원의 로그인 토큰과 브라우저 저장소에 실린다(SQL ① 실행 뒤 토큰이 갱신될 때까지). ③ 번호는 SQL ① 을 **처음** 실행할 때 프로필로 옮겨지는데, 수집 동의 시각이 가입 시각이 아니라 SQL 실행 시각으로 남는다 |
| SQL ② 를 SQL ① 보다 먼저 | 실행 자체가 거절된다(`20261002000000_phone.sql 을 먼저 실행해 주세요`). 바뀌는 것 없음 |
| SQL ② 를 사이트보다 먼저 | 옛 화면에서 번호 없는 회원의 알림 신청만 실패한다 |

번호의 기준은 `public.profiles.phone` 하나다. 가입할 때 받은 번호는 프로필에 옮긴 뒤 가입 정보(`auth.users.raw_user_meta_data`)에서 지운다.

**SQL ① 을 다시 실행할 때**

다시 실행해도 프로필의 번호와 동의는 바뀌지 않는다. 가입 정보의 번호 사본은 프로필에 이미 번호가 있거나 옮길 수 없는 것(형식 오류, 필수 동의 없음)만 지운다.
프로필로 옮길 수 있는데 아직 옮겨지지 않은 사본은 지우지도 옮기지도 않는다. 옛 가입 트리거가 잠시 돌아온 사이(옛 `…_members.sql` 을 다시 실행했거나 되돌리기를 중간에 멈춘 경우)에 가입한 회원의 번호일 수 있어서다.
실행 뒤 1번의 확인 조회가 `0` 이 아니면 아래 순서로 정리한다.

1. 누구의 번호가 남았는지 본다.

```sql
select u.email, u.created_at, u.raw_user_meta_data ->> 'phone' as meta_phone, p.phone as profile_phone
from auth.users u left join public.profiles p on p.id = u.id
where jsonb_typeof(u.raw_user_meta_data) = 'object' and u.raw_user_meta_data ? 'phone';
```

2. 삭제 요청으로 번호를 지운 회원이 섞여 있으면 9-2 의 두 번째 문장으로 그 회원의 사본부터 지운다(옮기면 지운 번호가 되살아난다).
3. 남은 번호를 프로필로 옮긴다. 문자 수신 동의는 옮기지 않는다.

```sql
update public.profiles p
set phone = u.raw_user_meta_data ->> 'phone'
from auth.users u
where u.id = p.id and p.phone is null and p.privacy_agreed_at is not null
  and jsonb_typeof(u.raw_user_meta_data) = 'object'
  and regexp_replace(regexp_replace(coalesce(u.raw_user_meta_data ->> 'phone', ''), '[^0-9]', '', 'g'), '^820?(1[016789])', '0\1')
      ~ '^(010[0-9]{8}|01[16789][0-9]{7,8})$';
```

4. SQL ① 을 한 번 더 실행하면 사본이 지워진다. 확인 조회가 `0` 인지 본다.

### 2-2. 운영 중인 프로젝트에 회원 후기 적용 (2026년 10월)

휴대전화 번호 변경(2-1)을 배포한 뒤에 적용한다. 2-1 의 SQL ② 를 아직 실행하지 않았더라도 이 절의 순서와는 관계없다(후기는 휴대전화 번호를 쓰지 않는다).

0. **예고와 점검.**
   - 개정 예고: 운영 중인 `main` 에 예고문 두 문단(`node supabase/local/privacy-dates.mjs notice`)과 개정안 전문 두 파일(`… preview <main 을 내려받은 폴더>` 가 만드는 `terms-next.html`·`privacy-next.html`)을 올린다. 올린 날이 공고일이다. 올린 뒤 `… live` 로 운영 사이트에 실제로 보이는지 확인한다.
   - 후기 페이지의 「후기 모음 안내」(기존 후기 모음 위의 문단)가 사실과 맞는지 대표가 확인하고(다르면 `reviews.html` 의 `#rvAbout` 을 고친 뒤) `… curation-ok` 를 실행한다.
   - 배포 직전에 `node supabase/local/privacy-dates.mjs` 를 실행한다. 약관과 처리방침, 후기 모음 안내, 미리보기 파일이 남았는지를 함께 본다. 「배포하지 않습니다」가 나오면 멈춘다(9절 첫 항목).
1. **SQL** `20261003000000_reviews.sql` 을 SQL Editor 에서 Run. 사이트 배포보다 먼저 실행한다.
   - `PostgreSQL 15 이상이 필요합니다` 로 끝나면 적용되지 않은 것이다. 대시보드 Settings → Infrastructure 에서 버전을 올린 뒤 다시 실행한다.
   - 확인: 지금 사이트에서 로그인, 마이페이지, 회원 관리 화면이 그대로 되는지 본다(기존 표·함수·권한은 건드리지 않는다).
   - 확인: `REVIEWS_MONITOR.md` 2절의 명령이 `200` 과 `[]` 를 돌려준다.
2. **사이트 배포.**
   - 비로그인으로 후기 페이지: 「회원 후기」 구역과 운영 기준, 로그인 안내가 보인다.
   - 시험 계정(관리자가 아닌 계정)으로 후기 1건 작성 → 다른 브라우저(비로그인)에서 `이름 첫 글자**` 로 보인다 → 고치기 → 지우기.
   - 관리자 화면: 숨김(사유 선택) → 비로그인 화면에서 사라지고 운영 기준의 「숨김 처리 현황」에 1건 → 작성 계정의 「내가 쓴 후기」에 사유와 메모 → `알림 보냄으로 기록` → 숨김 해제 → 수강 확인.
   - 시험 계정으로 숨김 처리된 글을 지우면 「14일 동안 새 후기를 올릴 수 없습니다」 안내가 나오고 「후기 쓰기」 버튼이 사라진다. 시험이 끝나면 9-3의 SQL 로 보류를 푼다.
   - 브라우저 개발자 도구의 네트워크 탭에서 `reviews_public` 응답에 `user_id`, 이메일, 실명이 없는지 본다.
   - Supabase 대시보드 Advisors → Security 에 후기 관련 오류·경고가 새로 생기지 않았는지 본다. `private.review_quota`·`review_ban`·`review_hold`·`review_moderation_log` 의 「RLS는 켜져 있는데 정책이 없음」 안내는 의도한 것이다(API 로 접근할 수 없게 둔 표다).
3. 후기 점검 작업(예약 작업)을 만든다. 이 저장소 밖에서 만든다. 조회 방법은 `REVIEWS_MONITOR.md`.

| 상황 | 결과 |
|---|---|
| SQL 을 먼저(권장) | 새 표·뷰·함수가 생길 뿐이다. 옛 화면은 그대로 동작한다 |
| 사이트를 먼저 | 후기 페이지의 「회원 후기」 구역과 히어로의 버튼이 숨겨진 채로 있고(큐레이션 후기는 평소대로), 회원 관리 화면에는 「회원 후기용 데이터베이스 설정이 아직 적용되지 않았습니다」 안내만 나온다. SQL 을 실행하면 새로고침부터 나타난다 |
| `reviews.sql` 을 `phone.sql` 보다 먼저 | 된다. 후기는 휴대전화 번호를 쓰지 않는다 |
| `reviews.sql` 을 `…_members.sql` 보다 먼저 | 실행이 거절된다(`20261001000000_members.sql 을 먼저 실행해 주세요`). 바뀌는 것 없음 |
| `reviews.sql` 을 다시 실행 | 후기·숨김·수강 확인·처리 기록·작성 제한·보류가 그대로다. 이 파일의 옛 판(사유 이름이 「욕설·비방」「기타」이던 판)을 실행한 DB 에 덧실행해도 되고, 그때는 사유 이름만 새 이름으로 옮겨진다 |
| 되돌리기 | 사이트는 이전 커밋으로 되돌리면 구역이 사라진다. DB 는 그대로 둬도 해가 없다. 지우려면 `supabase/reviews-rollback.sql`(후기 전체가 지워진다. 먼저 관리자 화면에서 CSV 두 개를 받아 둔다) |

## 3. 로그인 설정

### 3-1. 주소 (Authentication → URL Configuration)
- **Site URL**: `https://snucoach.github.io`
- **Redirect URLs** → Add URL: `https://snucoach.github.io/**`

### 3-2. 이메일 로그인 (Authentication → Sign In / Providers → Email)
- Enable Email provider: 켬
- **Confirm email: 켬** (인증 메일을 눌러야 가입 완료)
- Secure email change: 켬
- **Minimum password length: 8**
- Password requirements: **Letters and digits**
- Email OTP Expiration: `3600` (1시간. 메일 문구가 ‘1시간 유효’로 되어 있음)

### 3-3. 메일 발송 서버 (필수)
Supabase 기본 메일은 **프로젝트 팀원 주소로만** 보내고 시간당 2통으로 제한된다.
그대로 두면 실제 회원에게 인증 메일이 가지 않는다(화면에는 ‘지금은 메일을 보낼 수 없어요’가 나옴).
아래처럼 Gmail을 연결한다.

1. 메일을 보낼 Gmail 계정에서 Google 계정 → 보안 → **2단계 인증 켜기**
2. Google 계정 → 보안 → **앱 비밀번호** → 이름 `supabase` → 16자리 비밀번호 복사
3. Supabase → Authentication → **Emails → SMTP Settings** → Enable custom SMTP
   - Sender email: 그 Gmail 주소
   - Sender name: `스누코치`
   - Host: `smtp.gmail.com`
   - Port: `465`
   - Username: 그 Gmail 주소(전체)
   - Password: 2번의 앱 비밀번호
4. 저장 후 Authentication → Rate Limits 에서 이메일 발송 한도(기본 시간당 30통)를 확인한다.

> Gmail 개인 계정은 하루 약 500통까지 보낼 수 있다. 회원이 많아지면 도메인을 사서 Resend 같은 메일 서비스로 바꾼다.
> 보낸 메일은 Gmail ‘보낸편지함’에 남으니 주기적으로 지운다(회원 이메일 주소가 들어 있음).

### 3-4. 한국어 메일 (Authentication → Emails → Templates)
두 개만 바꾸면 된다. 제목(Subject)은 아래 그대로, 본문(Body)은 파일 내용을 통째로 붙여 넣는다.

| 템플릿 | Subject | Body |
|---|---|---|
| **Confirm signup** | `[스누코치] 이메일 인증을 완료해 주세요` | `supabase/templates/confirm-signup.html` |
| **Reset Password** | `[스누코치] 비밀번호 재설정 안내` | `supabase/templates/reset-password.html` |

이 템플릿의 링크는 회원이 **가입한 기기와 다른 기기**(예: PC에서 가입, 휴대폰에서 메일 확인)에서 눌러도 동작한다.
기본 영어 템플릿을 그대로 두면 다른 기기에서 누를 때 실패하므로 꼭 바꾼다.

## 4. 사이트에 키 넣기

Supabase → **Project Settings → API Keys** (또는 Connect 버튼)에서 두 값을 복사한다.

- **Project URL**: `https://xxxxxxxx.supabase.co`
- **Publishable key**: `sb_publishable_...` 로 시작하는 키 (예전 프로젝트는 `anon` `public` 키)

`assets/js/auth-config.js` 의 `url` 과 `key` 에 넣고 커밋한다. (Claude에게 두 값을 알려 주면 대신 넣는다.)

> **절대 넣으면 안 되는 값**: Secret key(`sb_secret_...`), `service_role` 키, DB 비밀번호.
> 이 파일은 누구나 볼 수 있다. 비밀 키가 들어가면 아무나 전체 회원 정보를 읽고 지울 수 있다.
> 실수로 넣으면 사이트가 회원 기능을 멈추고, 매일 도는 GitHub 점검이 실패 메일을 보낸다. 그 즉시 Supabase에서 키를 폐기·재발급한다.

Publishable key는 원래 공개용이다. 회원 정보는 2단계의 보안 규칙(RLS)이 지킨다.

## 5. 관리자 지정

1. 사이트에서 대표 계정으로 회원가입·이메일 인증까지 마친다.
2. SQL Editor 에서 아래를 실행한다(이메일만 바꿔서).

```sql
update public.profiles set is_admin = true
where id = (select id from auth.users where email = '관리자@이메일.com');
```

3. 마이페이지에 ‘회원 관리(관리자)’ 버튼이 생긴다. 회원 목록(휴대전화 번호, 이메일·문자 수신 동의 여부 포함)·검색·CSV 내려받기를 할 수 있다.
   - `이메일 수신 동의 회원만`·`문자 수신 동의 회원만`을 켜면 그 방법의 수신에 동의했고 이메일 인증·가입 마무리를 끝낸 회원(발송 대상)만 남는다. 위쪽 통계의 수신 동의 수도 같은 기준이다.
   - 메일 인증을 끝내지 않은 계정의 동의는 표와 CSV 에 `동의(메일 인증 전)`으로 적힌다. 번호를 인증하지 않고 받으므로 남의 번호일 수 있다. CSV 의 `이메일 발송 대상`·`문자 발송 대상` 칸이 `대상`인 행에만 보낸다.
   - 알림 신청 목록의 `보내는 방법`: `이메일·문자`는 번호를 받은 뒤에 신청한 알림, `이메일만`은 번호를 받기 전에 신청한 알림이다(9-1).
4. 같은 화면 아래의 「회원 후기」에서 후기를 관리한다. 쓰기 전에 9-3(운영 수칙)을 읽는다.
   - `숨김`: 사유를 고르고 숨긴다. 사유 이름은 약관 제10조 제5항 각 호와 같다(`욕설·인신공격` / `광고·스팸` / `개인정보 노출` / `허위 사실·권리 침해` / `법령 위반` / `임시 조치(권리 침해 신고)`). `법령 위반`과 `임시 조치`는 메모가 필수다. 숨긴 글은 공개 조회에서 빠지고, 작성자는 「내가 쓴 후기」에서 사유와 메모를 본다(메모는 작성자가 읽을 문장으로 쓴다).
   - 숨긴 뒤 화면에 나오는 `작성자에게 메일 쓰기`로 그날 안에 사유와 이의 제기 방법을 알리고, 보낸 뒤 `알림 보냄으로 기록`을 누른다. 기록은 처리 기록에 남고(받는 사람과 메일 내용은 남지 않는다) 상태 칸에 날짜가 보인다. 나중에 보낸 경우에는 그 줄의 `알림 기록`에서 어떤 안내였는지 골라 남긴다.
   - `임시 조치(권리 침해 신고)`: 권리 침해 신고를 받았는데 판단이 어려울 때만 쓴다. 상태 칸에 기한(숨긴 날부터 30일)이 보인다. 그 안에 `사유 고치기`로 사유를 정하거나 `숨김 해제`를 한다. 그대로 두면 29일이 지난 뒤 정리 작업이 자동으로 다시 게시하고 처리 기록에 남긴다.
   - `숨김 해제`·`확인 취소`는 한 번 더 눌러야 실행된다. 해제한 뒤에는 화면의 `작성자에게 결과 메일 쓰기`로 결과를 알리고 기록한다. 이의를 검토했는데 숨김을 유지할 때는 그 줄의 `이의 결과 메일`을 쓴다. `사유 고치기`는 숨김 사유와 메모만 바꾼다.
   - 상태 선택의 `확인할 글`: 숨긴 뒤 작성자가 고친 글(다시 보고 기준에 해당하지 않으면 해제한다), 다른 후기를 숨긴 뒤 같은 회원이 올리거나 고친 글(숨긴 내용을 옮겨 적지 않았는지 본다), 기한이 7일 이내로 남은 임시 조치, 작성자 알림 기록이 없는 숨김 글이 모인다.
   - `수강 확인`: 학습코칭·생기부 컨설팅 후기에만 버튼이 나온다. 작성자가 프로그램을 바꾸면 자동으로 해제된다.
   - 관리자 계정으로는 후기를 쓰거나 고칠 수 없다. 관리자가 되기 전에 그 계정으로 쓴 글은 스스로 숨기거나 수강 확인을 붙일 수 없다(지우기는 된다). 후기를 지우는 버튼은 없다(숨김만 한다).
   - `CSV 내려받기`는 화면에 보이는 후기 목록, `처리 기록 CSV`는 숨김·사유 수정·해제·수강 확인·작성자 알림을 처리한 내역이다. 처리 기록에는 작성자와 본문이 없고, 글이 지워진 뒤에도 3년 동안 남는다.
   - 목록 아래 줄의 「숨긴 글의 별점」은 숨김이 낮은 별점에 쏠려 있지 않은지 스스로 점검하는 용도다.

   - 대상: **외부(External)**, 연락처 이메일: 스누코치 Gmail → 만들기
3. **클라이언트** → **클라이언트 만들기**
   - 애플리케이션 유형: **웹 애플리케이션**, 이름 `snucoach-web`

   - 만들기 → **클라이언트 ID**와 **클라이언트 보안 비밀번호** 복사

## 8. 일시정지 방지와 유지 관리

- 무료 플랜은 일주일 동안 DB 활동이 거의 없으면 **일시정지**된다(데이터는 보존, 로그인 불가).
  `.github/workflows/supabase-keepalive.yml` 이 매일 한 번 데이터 없는 함수(`ping`)를 호출해 이를 막는다.
- GitHub는 저장소에 60일 동안 커밋이 없으면 예약 작업을 끈다. 꺼졌다는 메일이 오면 저장소 **Actions** 탭에서 다시 켠다.
- 그래도 일시정지되면 Supabase 대시보드에서 **Restore** 를 누른다.
- 회원 기능이 매출에 중요해지면 Pro 플랜(월 25달러, 일시정지 없음·자동 백업)을 검토한다.

### 9-1. 광고성 정보(이메일·문자)를 보낼 때 (정보통신망법 제50조)

법 조항 해석이 들어간 항목이다. **처음 보내기 전에** 한국인터넷진흥원의 「불법스팸 방지를 위한 정보통신망법 안내서」 원문이나 불법스팸대응센터(국번 없이 118), 전문가 검토로 한 번 대조한다.

누구에게 보낼 수 있나
- [ ] 광고성 정보(학습 자료·이벤트·코칭 프로그램 안내, 상담 권유 등)는 **그 채널에 동의한 회원에게만** 보낸다. 이메일은 ‘이메일 수신’, 문자는 ‘문자 수신’. 2026년 10월 개정 전에 이메일만 동의한 회원은 문자 동의자가 아니다
- [ ] 문자 발송 대상은 회원 관리 화면에서 `문자 수신 동의 회원만`을 켜고 CSV 를 내려받아 쓴다. 보내기 직전에 다시 내려받고(철회 반영), 내려받은 파일은 보낸 뒤 지운다
- [ ] **필터 없이 받은 CSV 로 발송 대상을 추리지 않는다.** 꼭 써야 하면 `문자 발송 대상`(이메일은 `이메일 발송 대상`) 칸이 `대상`인 행만 쓴다. `동의(메일 인증 전)`은 본인 번호인지 확인되지 않은 계정이다
- [ ] 신청하지 않은 회원에게 상담·코칭을 먼저 권하는 문자는 광고다(문자 수신 동의자에게만). 전화(음성)로 권유하지 않는다. 하게 되면 동의 문구·처리방침·기록 열부터 다시 정한다
- [ ] 휴대전화 번호는 인증하지 않고 받는다. 본인 번호가 아니라는 연락이 오면 바로 9-2 의 ‘번호 삭제’를 한다(번호를 지우면 문자 수신 동의도 꺼진다). 같은 번호가 다른 계정에도 있는지 `select u.email from public.profiles p join auth.users u on u.id = p.id where p.phone = '01012345678';` 로 보고 함께 지운다
- [ ] 공지 문자(서비스 변경·장애·약관 개정 안내 등)에는 프로그램·이벤트·상담 안내를 넣지 않는다. 한 줄이라도 넣으면 광고성 정보이므로 문자 수신 동의자에게만, 아래 규칙대로 보낸다

문자·메일에 꼭 넣을 것
- [ ] 광고성 문자: 본문 맨 앞에 `(광고)`, 보내는 이(스누코치)와 연락처, 본문 끝에 **무료 수신거부 방법**(예: `무료수신거부 080-…`). 문자 발송 서비스는 080 무료 수신거부 번호를 제공하는 곳으로 고른다. 답장으로 거부하게 하면 수신자에게 요금이 들고, 마이페이지 스위치는 로그인이 필요하므로 이 둘만으로는 부족하다
- [ ] 광고성 메일: 제목 맨 앞에 `(광고)`, 본문에 보내는 이의 명칭·연락처·주소와 로그인 없이 할 수 있는 수신거부 방법(회신 등)
- [ ] 광고성 문자는 **21시부터 다음 날 8시까지 보내지 않는다**(야간 수신 동의를 따로 받지 않았다)

수신거부·동의 관리
- [ ] 수신거부가 들어오면 바로 반영하고, 처리 결과(보내는 이, 거부한 날짜, 처리 내용)를 14일 안에 알린다. 가입할 때 체크 한 번으로 이메일·문자를 함께 동의받으므로, **채널을 특정하지 않은 거부는 두 채널 모두 끈다**

```sql
-- 번호로 들어온 수신거부(채널을 특정하지 않음): 이메일·문자 모두 끈다
update public.profiles set marketing_sms_opt_in = false, marketing_opt_in = false where phone = '01012345678';
-- 문자만 거부한다고 밝힌 경우
update public.profiles set marketing_sms_opt_in = false where phone = '01012345678';
```

- [ ] 수신거부한 번호를 따로 목록으로 보관하지 않는다(처리방침에 없는 처리다). 수신거부는 회원 DB 의 동의 값을 끄는 것으로 처리하고, 보내기 직전에 CSV 를 다시 내려받아 반영한다. 같은 번호가 다른 계정에 다시 등록되는 경우까지 막으려고 목록을 따로 두려면, 먼저 처리방침 제1조에 그 처리(목적·항목·보유 기간)를 추가한다
- [ ] 수신 동의한 회원에게 **동의한 날부터 2년마다** 수신 동의 여부를 다시 확인해 알린다(이메일·문자 각각, 회원 관리 목록의 동의 일시 기준)
- [ ] 가입·가입 마무리·번호 입력 카드·마이페이지 스위치는 동의·철회를 처리한 직후 화면에 처리 결과(일자·채널)를 보여 준다. 따로 보낼 필요는 없다

목표 대학 입시 정보 알림
- [ ] 알림 발송물에도 **위 광고성 정보 규칙을 적용하는 것을 기본으로 한다**(`(광고)` 표기, 무료 수신거부, 야간 금지, 처리 결과 통지, 2년 재확인). 적용하지 않으려면 처음 보내기 전에 안내서 원문이나 118 로 확인한다
- [ ] 알림에 상담 신청 링크나 이벤트·코칭 문구가 한 줄이라도 들어가면 전체가 광고성 정보다
- [ ] 알림은 신청한 회원에게만, 그 회원이 신청할 때 화면에 적혀 있던 방법으로 보낸다. **문자 알림은 번호를 받은 뒤에 신청한 알림에만 보낸다.** 2026년 10월 개정 전에 신청한 회원은 「이메일로 보내 드립니다」 화면에서 신청했으므로, 나중에 번호를 입력했더라도 그 신청분은 이메일로만 보낸다(문자로도 받으려면 마이페이지에서 해제한 뒤 다시 신청하게 한다)
- [ ] 문자 알림 대상은 회원 관리 화면의 알림 신청 목록(CSV)에서 `보내는 방법`이 `이메일·문자`인 행이다. `이메일만`인 행에는 문자를 보내지 않는다. **문자를 보내기 전에 아래 조회로 한 번 더 확인한다**(문자로 보낼 수 없는 알림 신청: 번호가 없거나, 번호를 받기 전에 신청한 것)

```sql
select a.univ, u.email, p.phone, a.created_at, p.phone_agreed_at
from public.target_alerts a
join auth.users u on u.id = a.user_id
left join public.profiles p on p.id = a.user_id
where p.phone is null or p.phone_agreed_at is null or a.created_at < p.phone_agreed_at
order by a.univ, a.created_at;
```


### 9-2. 휴대전화 번호 삭제·정정 요청을 받았을 때

회원은 마이페이지에서 번호를 직접 바꿀 수 있다. 삭제 요청은 SQL Editor 에서 아래를 실행한다(이메일만 바꿔서). 번호를 지우면 문자 수신 동의도 함께 꺼지고 철회 시각이 남는다.

```sql
update public.profiles set phone = null
where id = (select id from auth.users where email = '회원@이메일.com');
-- 가입 정보에 사본이 남아 있을 경우를 대비해 함께 지운다(보통은 가입할 때 이미 지워져 있다)
update auth.users set raw_user_meta_data = raw_user_meta_data - 'phone' - 'marketing_sms'
where email = '회원@이메일.com';
```

번호가 없어진 회원은 다음에 마이페이지에 들어오면 번호 입력 카드를 다시 본다. 이미 신청한 알림은 남아 있으므로, 알림도 원하지 않으면 마이페이지에서 해제하거나 탈퇴하도록 안내한다.

### 9-3. 회원 후기 운영 수칙

법 조항 해석이 들어간 항목이다(표시광고법 제3조, 전자상거래법 제21조·제21조의4, 정보통신망법 제44조의2, 개인정보 보호법). 전문가 검토나 원문 대조를 한 번 거친다. 약관 제10조와 후기 페이지의 「운영 기준」이 아래와 같은 내용을 공개하고 있으므로, 수칙을 바꾸면 그 둘도 함께 고친다.

숨김
- [ ] 숨김은 운영 기준 다섯 가지(약관 제10조 제5항)에 해당할 때와 권리 침해 신고에 따른 임시 조치(제8항)에만 한다. 낮은 평점, 불만, 비판은 숨김 사유가 아니다. 불리한 후기만 골라 숨기거나 지우면 소비자를 속이는 행위로 볼 수 있다
- [ ] **운영 기준은 별점과 관계없이 같은 잣대로 적용한다.** 한 건을 숨길 때는 같은 위반이 있는 다른 후기(좋은 평점 포함)도 함께 살펴 같은 기준으로 처리한다
- [ ] 스누코치나 코치에 대한 비판은 「욕설·인신공격」「허위 사실·권리 침해」「임시 조치」로 숨기지 않는다. 숨길 수 있는 것은 욕설·인신공격·모욕과, 기록으로 확인되는 허위뿐이다. `효과가 없었다`, `불친절했다` 같은 의견과 평가는 허위 사실이 아니다
- [ ] 「허위 사실」은 객관적으로 확인되는 경우에만 고른다(예: 수강한 적이 없는 사람이 수강 경험을 지어낸 것이 기록으로 확인될 때)
- [ ] 「광고·스팸」의 「이용 경험과 관계없는 글」은 다른 업체 홍보나 뜻 없는 글자 나열 같은 글이다. 상담·환불·응대에 대한 불만은 후기다. 숨기지 않는다
- [ ] 「법령 위반」은 메모가 필수다. 어느 법령의 무엇에 어긋나는지 적는다
- [ ] **코치 이름**: 스누코치 소속 코치의 성명만 적은 후기는 「개인정보 노출」이 아니다(약관 제10조 제5항 제3호, 후기 페이지의 운영 기준과 작성 폼, 숨김 창의 안내에 같은 문장으로 적었다). 코치의 연락처·학교·사는 곳 등이 함께 드러난 경우에만 숨긴다. 좋은 평점의 후기에는 두고 나쁜 평점의 후기에만 적용하지 않는다. 이 기준을 바꾸려면 네 곳을 함께 고친다
- [ ] 메모는 작성자에게 구체 사유로 보인다(내가 쓴 후기, 안내 메일). 어느 기준에 왜 어긋나는지를 작성자가 읽을 문장으로 쓰고, **후기 문장을 그대로 옮겨 적지 않는다**(처리 기록은 후기 본문을 담지 않기로 약속했다). 이름·연락처 같은 개인정보와 신고한 사람이 누구인지도 적지 않는다

알림과 이의 제기
- [ ] **숨긴 날 작성자의 가입 이메일로 사유와 이의 제기 방법을 알린다**(관리자 화면의 `작성자에게 메일 쓰기`). 보낸 뒤 `알림 보냄으로 기록`을 눌러 처리 기록에 남긴다(약관이 「지체 없이 이메일로 알린다」고 약속하므로, 알렸다는 것을 나중에 보일 수 있어야 한다). 권리 침해 신고로 숨긴 경우에는 신고한 사람에게도 처리 결과를 알린다
- [ ] 작성자가 이의를 제기하거나 글을 고쳤다고 알려 오면 내용을 다시 보고, 기준에 해당하지 않거나 고쳐서 해당하지 않게 됐으면 바로 숨김을 해제하고 결과를 알린다(`작성자에게 결과 메일 쓰기`). 숨김을 유지할 때도 결과와 이유를 알린다(`이의 결과 메일`). 작성자가 알리지 않고 고치기만 한 글은 `확인할 글`에 모이므로, 숨긴 글이 있는 동안에는 며칠에 한 번 그 목록을 본다
- [ ] 권리 침해 신고(사생활 침해, 명예훼손 등)를 받으면 지체 없이 판단한다. 판단이 어렵거나 다툼이 예상되면 사유를 `임시 조치(권리 침해 신고)`로 골라 숨기고(메모에 신고 받은 날을 적는다. 신고한 사람이 누구인지는 적지 않는다) **30일 안에** 양쪽 소명을 확인해 사유를 정해 고치거나 해제한다. 그대로 두면 29일이 지난 뒤 자동으로 다시 게시된다(약관 제10조 제8항의 「정하지 못하면 다시 게시」)
- [ ] **스누코치와 소속 코치의 업무에 대한 평가·비판은 권리 침해 신고로 숨기지 않는다.** 대표나 코치가 신고인이 되어 비판 후기를 임시로 숨기면 불리한 후기를 가리는 것이 된다. 제5항에 해당할 때만 숨긴다
- [ ] 지금 숨김 처리된 후기의 사유별 건수는 후기 페이지의 「운영 기준」에 자동으로 나온다(숨김 조치가 있었음을 알리는 용도)

수강 확인
- [ ] 「수강 확인」은 코칭 관리 시트 등 수강 기록과 이름·이메일을 대조해 확인된 학습코칭·생기부 컨설팅 후기에만 붙인다. 확인되지 않았는데 붙이면 거짓 표시가 된다
- [ ] **별점·내용과 관계없이 수강 사실이 확인되는 모든 후기에 같은 기준으로 붙인다.** 낮은 별점 후기의 확인을 미루거나 빼거나 취소하지 않는다. 취소는 착오로 붙인 경우에만 한다

하지 않는 것
- [ ] 대표·코치·직원이 회원인 것처럼 후기를 쓰지 않는다(관리자 계정의 작성은 DB 가 막는다. 다른 계정으로도 쓰지 않는다). 약관 제10조 제1항과 후기 페이지의 운영 기준에도 적었다
- [ ] **SQL 로 후기를 넣거나 옮기지 않는다.** 카카오톡 등으로 받은 후기는 위쪽 후기 모음(큐레이션 영역)에만 싣는다. 회원 후기 구역에 넣으면 「회원이 직접 올린 후기」라는 표시가 거짓이 된다
- [ ] 불만 후기를 쓴 회원에게 수정·삭제를 부탁하거나 대가를 제시하지 않는다. 연락은 불만을 해결하려는 목적으로만 한다
- [ ] 할인·사은품 등 대가를 주고 받은 후기는 그 사실을 후기에 표시해야 한다(약관 제10조 제1항과 작성 폼에 「대가를 받고 쓰는 후기는 그 사실을 밝힌다」고 적었다). 지금은 표시 기능이 없어 작성자가 본문에 적는 것에 기댄다. 대가를 주는 후기 이벤트를 하려면 먼저 표시 기능을 넣는다
- [ ] 후기를 블로그·인스타그램·광고에 옮겨 쓰려면 작성자의 동의를 따로 받는다(약관 제10조 제2항)

되풀이 위반과 삭제
- [ ] 숨김 처리된 글을 작성자가 스스로 지우면 그 계정은 14일 동안 새 후기를 올릴 수 없다(약관 제10조 제10항. 숨긴 글을 지우고 같은 내용을 새 글로 올려 숨김을 없던 일로 만드는 것을 막는다). 이미 올린 글을 고치고 지우는 것과, 숨김 처리된 글을 고쳐 다시 게시를 요청하는 것은 그대로 된다. 이의가 받아들여졌거나 착오였으면 아래 SQL 로 보류를 푼다
- [ ] 숨김 처리된 내용을 자기의 다른 후기에 옮겨 적는 것은 DB 가 막지 않는다. 관리자 화면의 `확인할 글`에 「이 회원의 다른 후기를 숨긴 뒤에 올리거나 고친 글」로 표시되므로 보고 같은 기준으로 처리한다. 되풀이되면 작성을 제한한다(약관 제10조 제10항). 제한하기 전에 사유를 알린다
- [ ] **남은 위험: 작성 제한과 보류는 탈퇴한 뒤 같은 이메일로 다시 가입하면 풀린다.** 탈퇴하면 회원 정보를 즉시 삭제한다고 약관과 처리방침에 약속했기 때문에 제한 기록도 함께 지운다. 막으려면 탈퇴한 회원의 이메일을 알아볼 수 없게 바꾼 값(해시)을 일정 기간 보관해야 하고, 그러려면 처리방침에 「부정 이용 방지 목적의 보관」을 먼저 적어야 한다. 넣기 전까지는 다시 가입해 되풀이하는 글을 후기 점검(예약 작업)과 관리자 화면에서 보고 숨긴다

```sql
-- 후기 작성 제한(이메일과 사유만 바꿔서). 제한된 회원은 새 후기를 쓰거나 내용을 고칠 수 없다(지우기는 된다)
-- 실행 결과가 1행(user_id)인지 꼭 확인한다. 0행이면 이메일이 틀려 아무도 제한되지 않은 것이다.
insert into private.review_ban (user_id, reason)
select id, '숨김 처리된 광고 글을 되풀이해 올림' from auth.users where lower(email) = lower('회원@이메일.com')
on conflict (user_id) do update set reason = excluded.reason
returning user_id;
-- 제한 풀기(결과가 1행인지 확인)
delete from private.review_ban where user_id = (select id from auth.users where lower(email) = lower('회원@이메일.com')) returning user_id;
-- 지금 제한된 회원
select u.email, b.reason, b.created_at from private.review_ban b join auth.users u on u.id = b.user_id;
-- 숨김 처리된 글을 지워 새 글이 보류된 회원과 끝나는 시각
select u.email, h.until from private.review_hold h join auth.users u on u.id = h.user_id where h.until > now();
-- 보류 풀기(결과가 1행인지 확인)
delete from private.review_hold where user_id = (select id from auth.users where lower(email) = lower('회원@이메일.com')) returning user_id;
```

- [ ] 법원 결정 등으로 DB 에서 지워야 할 때만 SQL Editor 에서 `delete from public.reviews where id = 번호;` 를 실행한다. 먼저 관리자 화면에서 숨김 처리하고 CSV 를 내려받아 둔다. 그 밖의 경우에는 지우지 않고 숨기기만 한다
- [ ] 처리 기록(`private.review_moderation_log`)은 고치거나 지우지 않는다. 3년이 지나면 자동으로 지워진다(처리방침 제2조)

## 10. 문제 해결

| 증상 | 원인과 조치 |
|---|---|
| ‘지금은 메일을 보낼 수 없어요’ | 3-3 SMTP 미설정. 기본 메일은 팀원에게만 간다 |
| 인증 메일이 안 온다 | 스팸함 확인 → Authentication → Logs 에서 오류 확인 → Gmail 앱 비밀번호 재발급 |
| ‘링크가 만료되었거나 이미 사용되었어요’ | 1시간이 지났거나 이미 누른 링크. 로그인 화면에서 인증 메일 다시 받기 |
| 다른 기기에서 메일 링크를 누르면 실패 | 3-4 한국어 템플릿을 아직 안 바꿈 |
| 로그인 메뉴가 안 보인다 | `auth-config.js` 가 비어 있음. 바꾼 뒤 최대 10분 캐시가 있다 |
| ‘서버에 연결하지 못했어요’ | 프로젝트 일시정지 여부 확인(대시보드 Restore) |
| 회원 관리 화면에 ‘관리자만 볼 수 있는 페이지’ | 5단계 SQL을 실행했는지, 그 계정으로 로그인했는지 확인 |
| 회원 관리에 ‘휴대전화 번호용 데이터베이스 설정이 아직 적용되지 않았습니다’ | `20261002000000_phone.sql` 을 실행한다 |
| 번호를 저장하면 ‘지금은 저장할 수 없습니다’ | 같은 파일이 적용되지 않았거나, 옛 파일을 다시 실행해 수정 권한이 지워졌다. `20261002000000_phone.sql` 을 다시 실행한다 |
| 가입 화면에 번호 칸이 있는데 마이페이지에는 번호가 안 보인다 | 사이트만 배포하고 SQL ① 을 아직 실행하지 않았다(순서 위반). 바로 실행한다. 그 사이 가입한 회원의 번호는 옮겨지지만 문자 수신 동의는 옮겨지지 않는다(2-1 의 표) |
| SQL ① 실행 뒤 확인 조회가 0 이 아니다 | 2-1 의 「SQL ① 을 다시 실행할 때」를 따른다 |
| 후기 페이지에 「회원 후기」 구역이 안 보인다 | `20261003000000_reviews.sql` 을 아직 실행하지 않았거나 `auth-config.js` 가 비어 있다 |
| 회원 관리에 ‘회원 후기용 데이터베이스 설정이 아직 적용되지 않았습니다’ | `20261003000000_reviews.sql` 을 실행한다 |
| 후기를 올리면 ‘지금은 후기를 올릴 수 없습니다’ | 같은 파일이 적용되지 않았거나 일부만 남았다. `20261003000000_reviews.sql` 을 다시 실행한다 |
| 후기 구역에 ‘후기를 불러오지 못했습니다’ | 프로젝트 일시정지 여부 확인(대시보드 Restore). 큐레이션 후기는 영향이 없다 |
| 후기를 쓰려는데 ‘관리자 계정으로는 후기를 쓸 수 없습니다’ | 의도한 동작이다(9-3). 시험은 관리자가 아닌 계정으로 한다 |
| 후기를 쓰려는데 ‘숨김 처리된 후기를 지워서 …까지 새 후기를 올릴 수 없습니다’ | 의도한 동작이다(숨김 처리된 글을 지운 뒤 14일 보류). 풀려면 9-3의 SQL |
| 관리자 화면에서 ‘데이터베이스 설정을 다시 실행해 주세요’ | `20261003000000_reviews.sql` 의 옛 판이 적용되어 있다. 지금 판을 다시 실행한다(후기와 처리 기록은 그대로다) |
| 관리자 화면에서 ‘본인 계정으로 쓴 후기는 직접 처리할 수 없습니다’ | 의도한 동작이다. 관리자 계정으로 쓴 글은 그 계정이 스스로 숨기거나 수강 확인을 붙일 수 없다 |

## 개발자용: 로컬 검증

실제 Supabase와 같은 구성(Postgres 17 · 인증 서버 GoTrue · REST · 메일 수신함)을 Docker로 띄워 전체 흐름을 검증한다.

```bash
cd supabase/local
./up.sh                                   # 스택 실행 + 마이그레이션 적용 (사이트: http://localhost:8080)
node api-tests.mjs                        # DB 권한·보안 규칙 검증
NODE_PATH="$(npm root -g)" node e2e.mjs   # 브라우저로 가입~탈퇴 전체 흐름 검증 (Playwright)
./down.sh                                 # 정리
node privacy-dates.mjs                    # (Docker 불필요) 배포 전 점검: 처리방침·약관 공고일·시행일, 후기 모음 안내 확인 여부, 미리보기 파일. 배포 직전에 실행한다
```

Docker 없이 도는 검증(회원 후기):

```bash
cd supabase/local
npm i --no-save @electric-sql/pglite      # 한 번만. node_modules 는 저장소에 올라가지 않는다
node reviews-db.mjs                       # 후기 마이그레이션: 실행 순서·여러 번 실행·권한·RLS·트리거·관리자 함수·공격 시나리오(PGlite)
node reviews-ui/ui.mjs                    # 후기 화면: 정적 서버 + 가짜 Supabase + 헤드리스 크롬(맥의 크롬. 다른 위치면 CHROME=/경로)
```

`reviews-ui/` 의 가짜 Supabase 클라이언트는 `server.mjs` 안에 있다(따로 `.js` 파일로 두지 않는다. 저장소 파일은 운영 사이트와 같은 출처로 공개되므로, 브라우저가 실행할 수 있는 가짜 클라이언트 파일을 두지 않는다).

`reviews-db.mjs` 는 실제 PostgreSQL 엔진으로 권한과 트리거를 보지만 인증 서버·REST API 는 없다. 직접 정한 오류 코드(`RV001` 등)가 API 로 그대로 오는지는 `api-tests.mjs`(Docker)가 본다.

메일 수신함: http://localhost:8025
